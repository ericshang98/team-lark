# Software 协作

飞书每行是一件工作，可关联多个 PR。GitHub 是 PR 状态证据；工作摘要、协调说明和安装/上线证据由负责人维护。入口是 `team-lark software`。先处理本入口，不执行父 Skill 的通用今日简报。

## 首次配置

需要 Python 3.10+、已登录的 `gh` 和 `lark-cli`。使用当前人自己的账号，核对 GitHub/Lark 身份映射。团队共用一份配置，保存在 `~/.team-lark/software.json`，只含 Base 坐标、仓库与成员映射，不含凭证；示例见 [config.example.json](config.example.json)。不要把团队配置、快照或 PR 正文提交到公开仓库。

已有团队表时直接使用共享配置，勿各建一份。用户要求初始化时运行 `python3 <本目录>/scripts/software.py setup`，复用同名表并验证 schema，建「软件协作」「软件动态」「软件阅读记录」。初始化后在软件协作表建按「开发状态」分组的 kanban 和按「负责人」分组的 grid，隐藏内部摘要/版本字段。配置可通过团队内部消息或文件共享。

## 每次运行

1. `python3 <本目录>/scripts/software.py sync`。自动查询全部 open PR、最近三天有更新的 PR，并逐一刷新看板已跟踪的更早 PR。查询失败保留旧数据，不推进阅读记录。已关闭 PR 只收集状态/提交等概要，不抓取全量历史 CI；报告会明确标注。需要指定历史范围时用 `--since YYYY-MM-DD`。
2. 读脚本报告和 `~/.team-lark/software-snapshot.json`，按「别人变化 → 我的变化 → 协调事项」给简报。报告展示相对当前人上次阅读的工作版本；动态表可追溯中间历史。强调本次覆盖范围、最后核实时间、CI/评审问题和具体下一步。模块重叠只是协调线索，不能断言代码冲突或依赖。
3. 若本会话有尚未登记的工作，先看当前工作区的 `git status`、diff/提交和 PR；只将必要的摘要、分支与链接同步，不上传整个 diff、日志或私有文件。开工写计划与模块，收工写实际变化及验证。没有 PR 的内容标为本地进行中，不推断另一台电脑的未提交工作。一次工作复用原「工作ID」，不要每次创建新行。
4. 写入自己的进展：生成本地 plan JSON 后运行 `sync --plan <path>`；先用 `--dry-run` 检查归组。一个 PR 只能属于一项工作，不能仅凭标题相似就随意归组。新发现但尚未归组的 PR 会先单独登记；归并已有记录涉及历史保留，第一版应在飞书明确迁移链接并保留原动态，不能静默删除。
5. 把报告实际展示给用户后，执行 `ack --receipt <报告回执路径>`。只确认本次实际展示的工作版本，不提前 ack、不替别人已读。若简报只展示部分工作，应先生成仅含已展示工作版本的回执再 ack。新变化不会被旧回执吞掉。`report` 只读远端、不确认阅读；可以随时重看。

所有命令也接受 `--config <path>`（放在子命令前）。`collect --output <path>` 只收集证据，适合历史归组；`sync --dry-run` 不写飞书、不推进阅读记录，但会保存本地快照。

## 提 PR / 合并后自动同步

在团队现有提交 PR 流程中，创建 PR、推送更新到已有 PR、确认实际合并成功后，自动调用：

```bash
python3 <本目录>/scripts/after_pr.py --pr <真实PR_URL> --event created
# 已有 PR 更新用 updated，实际合并成功用 merged
```

若项目有 `.agents/skills/commit-push-pr/scripts/sync-software.py`，优先使用该仓库入口；它会定位本机 Skill，并在缺少依赖时保留待补记录。不要为了看板同步再次创建或合并 PR。

钩子读取 GitHub 当前事实，只刷新该 PR 所属工作及其同组 PR，保留人工说明；新 PR 按完整 URL 查重，先用真实 PR 标题登记摘要。它不运行今日简报、不生成阅读回执、不改变已读、不发私信。其他人的未合并工作不会因这次事件被更新。已有本地计划需要归组时仍按 Plan 使用工作ID维护。

失败返回 2，原 Git 操作仍然成功；必须报告「Git 已完成，飞书待补同步」。待补事件在 `~/.team-lark/software-hooks/pending/`，下次调用自动补最多 5 项，同一 PR 多个事件合并处理，重新查最新状态；不会重放过期状态。可用 `after_pr.py --retry` 单独恢复。缺配置/登录失败保留队列，不默默丢弃；没有后台定时器。一个机器上的钩子使用文件锁串行写，跨机器冲突按下方恢复规则处理。

此自动化覆盖接入后的 Agent PR 流程，不监听绕过流程的 GitHub 网页操作。自动合并入队不是 MERGED，须以 GitHub实际状态为准。

## Plan

只填要更新的字段；省略的人工字段保留，传空字符串表示明确清空。`owner` 是配置中的 GitHub login，不根据名字猜 open_id。`module` 用英文逗号分隔统一模块名，如 `Cloud,Desktop,iOS`。

```json
{"works":[{"key":"login-recovery","owner":"my-github-login","title":"恢复登录后会话","module":"Cloud,Desktop","summary":"完成了什么、解决什么问题","coordination":"依赖哪个 PR，下一步由谁处理；未确认则明确待确认","validation":"验证命令/结果/证据链接；安装与上线单独记录","branch":"feature/login-recovery","prs":["https://github.com/example/project/pull/42"],"tasks":[]}]}
```

`tasks` 填已有任务表真实 record_id，仅创建关联，不改任务状态。普通运行只改自己负责的人工字段。只有用户明确要求整理团队历史时，可用 `--import-history` 导入别人的已有 PR/交接事实；注明来源与时间，不冒充本人表态，不改变现有任务负责人/验收人。

## 状态与恢复

- Draft → 开发中；未获批准 → 待评审；已批准 → 待合并；部分 PR 合并 → 部分合并；全部合并 → 已合并；全部关闭且未合并 → 已关闭。CI、mergeable 独立展示；「待合并」不承诺可以立即合并。
- 已合并不代表已安装/上线。历史说明注明「PR 作者报告」或「此前聊天记录」，不能充当本次实测。
- `最近核实UTC` 只是事实采集时间；重复核实不产生新动态。人工字段与机器字段均有实质变化才换版本；动态写失败，下次先补齐再更新。
- 不重复启动同一轮同步。Base 无跨记录事务或唯一约束；脚本会检查重复键、写前版本和写后结果，但不能保证跨机器同时写入的原子性。发现冲突/重复即停止，重新读取定位；不覆盖、不自动删行。两人同时操作优先只提交各自人工摘要，事实同步错开执行。
- 只读 `report` 仍会在本地生成报告/回执。GitHub 失败显示未核实，保留上次状态；脚本不会把错误写成空列表或完成。
- 软件同步不自动合并 PR、不部署、不安装、不派任务、不发私信。用户要求通知谁时才发给谁；没有定时器或后台常驻进程。
